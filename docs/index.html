Each run scored 200 MMLU questions with a different sampling seed, so most of the variation below is just that: different samples of the same model. The reason to chart it at all is to make the noise floor visible. Anything inside the Wilson CI on the overview tab is consistent with chance. Decisions

ADR-001: DuckDB as the primary warehouse

DuckDB is free, embedded, and runs anywhere with no setup, so the whole project clones and rebuilds in about ten minutes. A Snowflake target sits in profiles.yml alongside it. The dbt models are warehouse-portable; the demo just doesn't depend on a trial that expires.

ADR-002: Three Claude models, three runs each

Haiku 4.5, Sonnet 4.6, and Opus 4.7, each scored three times against a 200-question MMLU subset. Total API cost under $20. With only three trials the Wilson CIs are wide, which is the point: the bands make the noise floor visible instead of hiding it behind a single number.

ADR-003: Parsing lives in the raw layer

Both raw_completion and parsed_answer are stored at ingest time. If the regex needs fixing later, that's a SQL-only refresh; no API rerun. Staging stays a clean projection of what came back from the model.

ADR-004: No judge-model scoring

A judge model would resolve verbose or hedged completions better than a regex. It's out of scope for this build. Instead, unparseable_rate is tracked as its own metric so the regex's failures are visible rather than silently folded into "wrong".

Why this exists

Eval-data plumbing is the invisible thing

Every benchmark number you've seen ("MMLU 87%", "HumanEval 92%") sits on top of a pipeline that loaded the dataset, sampled it, called the model, parsed the output, joined to ground truth, and aggregated. When that pipeline breaks subtly, a prompt-template typo or a regex that quietly drops 3% of completions, the headline number lies. This project treats the pipeline as the thing that has to be trustworthy first: versioned schemas, lineage, freshness checks, idempotent reruns.

The load-bearing pieces

Every scoring run gets a UUID and the prompt-template version pinned to its git SHA. A UNIQUE constraint on (run_id, question_id) means reruns can't silently double-count. Wilson 95% CIs sit on every pass-rate cell because three trials of 200 questions isn't enough to claim a small difference is real. Parsing and scoring live in different layers, so fixing one doesn't require rerunning the other.

What this build can't tell you

Three runs per model is not enough for a real lab. They'd run hundreds. The "drift" between runs here is mostly sampling variance; real drift detection needs runs spaced out over time, ideally against the same prompt fingerprint. MMLU itself is saturated, so nothing here is a SOTA claim. It's a tooling demonstration.
